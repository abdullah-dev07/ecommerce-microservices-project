# E-Commerce Microservices (FastAPI)

A learning-focused microservices project: 3 independent services + 1 API Gateway,
each with its own PostgreSQL database, communicating over HTTP.

---

## Architecture

```
                 Client
                   │
                   ▼
          ┌─────────────────┐
          │   API Gateway   │  :8000 — only exposed port
          └────────┬────────┘
                   │ HTTP
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │  User  │ │Product │ │ Order  │
   │  Svc   │ │  Svc   │ │  Svc   │
   │ :8001  │ │ :8002  │ │ :8003  │
   └────┬───┘ └───┬────┘ └───┬────┘
        │         │          │
        ▼         ▼          ▼
   [user_db] [product_db] [order_db]
    :5433      :5434       :5435
```

The Order Service calls the User and Product services over HTTP to validate
data and reserve stock. Services are decoupled but cooperate.

```

    │       │   └── http_client.py         # shared AsyncClient + proxy()
    │       ├── schemas/                   # request bodies validated at the edge
    │       └── api/routes/                # health, users, products, orders
    ├── user_service/
    │   ├── pyproject.toml                 # Aerich config
    │   ├── migrations/                    # generated by Aerich
    │   └── app/
    │       ├── main.py
    │       ├── core/        (config, security, tortoise)
    │       ├── models/      (Tortoise ORM)
    │       ├── schemas/     (Pydantic)
    │       ├── services/    (business logic)
    │       └── api/routes/
    ├── product_service/                   # same layout
    └── order_service/                     # same layout + clients/
        └── app/
            ├── clients/
            │   ├── user_client.py         # outbound httpx → user_service
            │   └── product_client.py      # outbound httpx → product_service
            └── ...
```

### Why this layout

| Layer | Purpose | Knows about |
|---|---|---|
| `api/routes/` | HTTP shape: paths, status codes, request/response models | FastAPI |
| `services/` | Business rules ("create order = verify user, check stock, persist") | ORM + clients |
| `clients/` | Outbound calls to other microservices (timeouts, retries, error mapping) | `httpx` |
| `models/` | Tortoise ORM models | DB only |
| `schemas/` | Pydantic for I/O validation | nothing |
| `core/config.py` | Single typed source of env vars | `pydantic-settings` |
| `core/tortoise.py` | `TORTOISE_ORM` config consumed by app + Aerich | Tortoise |

## Quick start

```bash
cp .env.example .env
docker compose up --build
```

All services start automatically with isolated databases. Only the gateway
publishes a port (`:8000`). Open the interactive docs at
[http://localhost:8000/docs](http://localhost:8000/docs).

## API reference (via the Gateway)

### Health
```
GET    /health                   → gateway + downstream service status
```

### Users
```
POST   /users                    → create user
GET    /users/{id}               → get user
GET    /users                    → list users
```

### Products
```
POST   /products                 → create product
GET    /products/{id}            → get product
GET    /products                 → list products
```

### Orders
```
POST   /orders                   → create order (verifies user + stock, deducts stock)
GET    /orders/{id}              → get order
GET    /users/{id}/orders        → list orders for a user
PATCH  /orders/{id}/cancel       → cancel order (restores stock)
GET    /orders/{id}/detail       → aggregated: order + customer
```

## Test flow (curl)

```bash
BASE=http://localhost:8000

# 1. Create a user
curl -X POST $BASE/users \
  -H "Content-Type: application/json" \
  -d '{"name": "Alice", "email": "alice@example.com", "password": "supersecret123"}'

# 2. Create a product
curl -X POST $BASE/products \
  -H "Content-Type: application/json" \
  -d '{"name": "Laptop", "description": "Fast laptop", "price": 999.99, "stock": 10}'

# 3. Place an order
curl -X POST $BASE/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id": 1, "items": [{"product_id": 1, "quantity": 2}]}'

# 4. Aggregated detail
curl $BASE/orders/1/detail

# 5. Cancel — stock is restored
curl -X PATCH $BASE/orders/1/cancel
```

## Key learning points

| Concept | Where to look |
|---|---|
| One DB per service | `docker-compose.yml` |

## Database migrations (Aerich + Tortoise ORM)

Each DB-owning service (`user_service`, `product_service`, `order_service`)
uses **Tortoise ORM** for the data layer and **Aerich** as its migration tool
(Aerich is the official Tortoise migration tool — same role Alembic plays for
SQLAlchemy). Per-service migration files live in `services/<svc>/migrations/`.

### One-time bootstrap (per service)

The `migrations/` folder ships empty. The first time, generate the initial
migration and apply it:

```bash
# Make sure the DB container is up
docker compose up -d user_db

cd services/user_service
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL=postgres://postgres:password@localhost:5433/user_db

aerich init-db                  # creates migrations/models/0_<timestamp>_init.py + applies it
```

Repeat for `product_service` (port 5434) and `order_service` (port 5435).
**Commit the generated `migrations/models/*.py` files** — they are source.

### Day-to-day workflow

```bash
# 1) Edit a model — e.g. add a `phone` field to User in
#    services/user_service/app/models/user.py
#
#    phone = fields.CharField(max_length=20, null=True)

# 2) Generate a migration (Aerich autodetects the diff)
cd services/user_service
aerich migrate --name add_phone

# 3) Review migrations/models/<timestamp>_add_phone.py before applying.
#    Autogenerate is good but not perfect.

# 4) Apply it
aerich upgrade
```

### Useful commands

```bash
aerich init -t app.core.tortoise.TORTOISE_ORM   # one-time setup (already done via pyproject.toml)
aerich init-db                                  # first migration + create tables
aerich migrate --name <slug>                    # generate migration from model diff
aerich upgrade                                  # apply all pending migrations
aerich downgrade -v 1                           # roll back the last migration
aerich history                                  # list applied migrations
aerich heads                                    # show pending heads
```

### How it works under the hood

- `pyproject.toml` has `[tool.aerich]` pointing at `app.core.tortoise.TORTOISE_ORM`
  and `location = "./migrations"`.
- `app/core/tortoise.py` defines `TORTOISE_ORM` once. It's consumed by both
  the runtime (`Tortoise.init(config=TORTOISE_ORM)` in `app/main.py`) and by
  Aerich for diffing.
- `app.models` (the package) **must** import every model so Tortoise sees
  them. That's why each `app/models/__init__.py` re-exports its models.
- `aerich.models` is included in `TORTOISE_ORM` so Aerich can store its own
  bookkeeping table (`aerich`) in the same database.

### In Docker

The Dockerfile runs `aerich upgrade` automatically before starting uvicorn,
so `docker compose up --build` always brings the schema up to date — provided
you've committed at least one migration:

```dockerfile
CMD ["sh", "-c", "aerich upgrade && exec uvicorn app.main:app --host 0.0.0.0 --port 8001"]
```

In real production this is usually moved to a one-shot job (k8s `Job`, ECS
task, etc.) so two pods don't race to migrate at the same time. For local +
learning, in-container is fine.

### Rules of thumb

- **Never edit a migration that has been merged / shipped.** Add a new one.
- **Migrations are source code** — they live in `migrations/models/*.py`
  and MUST be committed to git.
- **Each service owns its own migration history.** `user_service` knows
  nothing about `product_service`'s migrations, and vice versa — that's
  the point of "DB per service."

## Suggested next steps

1. **Auth at the gateway** — issue JWTs from `user_service`, validate at the gateway,
   forward identity as `X-User-Id` to downstream services.
2. **Resilience** — add retries (`tenacity`) and circuit breakers (`pybreaker`)
   to the inter-service clients.
3. **Observability** — structured logging + OpenTelemetry tracing across services.
4. **Async messaging** — emit an `OrderCreated` event for emails / analytics
   instead of doing everything synchronously in the request path.
5. **Conditional stock UPDATE** — replace the read-modify-write in
   `product_service.update_stock` with a single conditional `UPDATE` (e.g.
   `Product.filter(id=..., stock__gte=qty).update(stock=F("stock") - qty)`)
   to fully avoid races under concurrency.
6. **Migrations in CI** — fail the build if Aerich detects model drift not
   captured in a migration file.
